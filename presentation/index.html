CyberScope asks: has this device moved away from its trusted state?

Problem / Method / Demo
IoT devices are being used more widely in everyday settings and critical environments, from smart homes to industrial and autonomous systems. All of these systems rely on sensor data they can trust. The I2Map research shows that an attacker who compromises an IoT device could change its hardware, software, network configuration or other settings. The device may continue operating, even though its data can no longer be assumed to be legitimate. CyberScope is designed to detect those unauthorised changes and show when a Raspberry Pi-based IoT device has moved away from its known trusted state. The statistics are findings from Dragos engagements, not prevalence estimates for all ICS owners. 56% cannot see below the IT/OT boundary; 88% struggle with detection and response.

Design & methodology.

Current activity

    We're using a Raspberry Pi VM as the IoT test device. Our proposed technology stack includes Python for collecting hardware, software, network and device configuration, and selected environmental parameters. The collected data will generate a SHA-256 integrity map, with Solidity smart contracts on a private Ethereum-compatible blockchain. The architecture has two stages: onboarding and runtime attestation. During onboarding, we collect the selected parameters while the device is known to be legitimate. These generate the Base I2Map, our approved trusted baseline, registered through the blockchain. During runtime, we repeat parameter collection and generate a runtime I2Map. If the hashes match, the monitored configuration is unchanged and sensor data is accepted. If they differ, sensor data is rejected and the administrator is alerted. This depicts our proposed architecture. The current repository contract stores and retrieves hashes; integrated comparison, data gating and sensor transactions remain proposed. Matching monitored state is not a guarantee that all sensor readings are legitimate. Environmental coverage depends on available measurements. We're building in modules and working to milestones: parameter collection, SHA-256 integrity-map generation, blockchain functionality and final integration. Team roles cover Raspberry Pi collection, integrity-map logic, blockchain development, security testing and performance evaluation. Once integrated, we'll validate through deliberate software changes, network/configuration modifications and unauthorised USB connection. We'll check for integrity mismatches, repeat unchanged-device checks to measure false positives, and record execution time, transaction commit time and memory usage.
